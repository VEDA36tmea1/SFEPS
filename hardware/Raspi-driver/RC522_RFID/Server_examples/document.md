# RC522 서버 연동 아키텍처 문서

## 추천 구조: Hardware Driver (C++) ↔ Unix Domain Socket ↔ Main Server

하드웨어 제어와 메인 서버를 **분리**하고, **Unix Domain Socket(UDS)** 으로 연동하는 구성을 권장합니다.

- **Hardware Driver**: C++ 데몬 (`rc522_uds_daemon`) — `/dev/rc522` 직접 접근, 카드 태깅 이벤트 수집.
- **Unix Domain Socket**: 로컬 프로세스 간 통신 경로.
- **Main Server**: Node.js, Python Flask 등 — UDS 클라이언트로 데몬에 연결해 이벤트 수신.

---

## IPC 방식 선택

### Step 1: Unix Domain Socket (UDS) 또는 파이프 — **현재 방식**

- **특징**: 로컬 프로세스 간 통신에서 가장 빠르고 지연이 적음.
- **용도**: 단일 라즈베리 파이 내부에서 서버와 하드웨어 앱이 긴밀하게 소통할 때 적합.
- **구현**: 데몬이 UDS 서버로 동작하고, 메인 서버가 해당 소켓에 connect 해 한 줄씩 NDJSON 수신.

### Step 2: MQTT (로컬 브로커 활용) — **추후 서버 확장 시 검토**

- **특징**: 발행/구독(Pub/Sub) 구조. 하드웨어 앱이 데이터를 발행하면 서버(또는 여러 구독자)가 구독해 가져감.
- **용도**: 서버를 여러 대로 확장하거나, 다른 서비스에서도 RC522 이벤트를 구독해야 할 때 고려.
- **현재**: 1번(UDS)으로 진행하고, **속도**를 우선. 추후 확장 시 2번(MQTT)으로 전환/병행을 검토.

## 왜 디바이스 직접 접근이 아닌, 별도 앱 + IPC 인가?

### 1. 디바이스 파일 직접 접근 (Direct Access)

서버 애플리케이션(예: Node.js, Python Flask 등)이 `/dev/rc522`(또는 `/dev/i2c-1`, `/dev/gpiomem` 등)를 직접 열어서 제어하는 방식입니다.

**장점**

- 구현이 단순하고 지연 시간(Latency)이 거의 없음.

**단점**

- **권한 문제**: 서버 앱이 root 권한이나 하드웨어 접근 권한 그룹에 속해야 하므로 보안에 취약해짐.
- **성능 저하**: 서버 앱이 웹 요청을 처리하면서 하드웨어의 **블로킹 I/O**까지 떠안으면 전체 서비스가 느려질 수 있음.
- **결합도 상승**: 하드웨어가 바뀌면 서버 전체 코드를 수정하고 재빌드해야 함.

### 2. 별도 앱 + 파이프/IPC 통신 (Decoupled Process)

C++(또는 Python)으로 하드웨어 제어 전용 **드라이버 앱(데몬)** 을 만들고, 메인 서버와는 **UDS 등 IPC**로만 통신하는 방식입니다.

**이 방식을 선택한 이유**

- **역할 분리 (Separation of Concerns)**: 서버는 비즈니스 로직과 클라이언트 응대만 담당하고, 하드웨어 앱은 데이터 수집만 담당함.
- **안정성**: 하드웨어 제어 앱에서 메모리 누수나 크래시가 나도 메인 서버는 영향받지 않음.
- **언어 최적화**: 서버는 생산성이 좋은 Python/JS로 작성하고, 하드웨어 제어는 성능과 실시간성이 중요한 **C++** 로 작성해 효율을 높일 수 있음.

위 이유로 **분리 구조**와 **IPC(우선 UDS)** 를 선택했습니다.
